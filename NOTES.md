## Task 5 — pooled hidden-state adapter: NaN-on-empty-row bug found and fixed, packing note for Task 7

- **Bug found by review, fixed before Task 7 wires this in:** `pool_state_token_hidden_states`'s 3D (batched) branch originally only validated `state_token_mask.any()` across the *whole* tensor, not per-row. An all-False mask on a single row in an otherwise-valid batch (e.g. shape `[2,3,2]`, mask `[[True,False,True],[False,False,False]]`) silently produced `[[2.,2.],[nan,nan]]` instead of raising — `.mean(dim=0)` over an empty selection is a silent NaN, not an exception. This is now fixed with a per-row check (`state_token_mask[i].any()`) that raises `ValueError(f"state_token_mask row {i} has no True positions to pool over")` identifying the offending row. Verified fixed: reproducing the exact `[2,3,2]` scenario above now raises instead of returning NaN. Added 3D test coverage (`tests/test_pooled_hidden_adapter.py`): a batched happy-path test and a per-row-empty-mask test — the 3D branch had zero test coverage before this fix (all original 3 tests only exercised the 2D single-sample path).

- **Why this matters for Task 7:** `compute_total_loss` (not yet built) has no runtime `isfinite` guard per current design. A silent NaN from this adapter would flow uncaught into the loss and permanently poison Adam's optimizer state (NaN moment estimates don't self-heal) — the kind of bug that surfaces hours into a training run with no clear proximate cause. Task 7's implementer should either keep relying on this ValueError as the guard (i.e. never suppress/catch it upstream without deliberately deciding what an empty-mask row *means* for that batch), or add an explicit `isfinite` check in `compute_total_loss` as defense in depth.

- **Real batch shape at Task 7's call site is probably NOT a genuine multi-row batch.** `vendor/Xiaomi-Robotics-1/xr1/mibot/data/collate/custom_collate.py` **packs** samples together via `torch.cat(dim=1)` (concatenating along the sequence dimension) rather than padding samples into independent rows of a batch, and it drops any sample that would overflow the packed length whole (not truncating it). This means the real `hidden_states`/`state_token_mask` tensors reaching this adapter from the primary JSON-dataset path (`xr1/mibot/data/datasets/json_dataset.py`) are likely shaped closer to `[1, total_packed_length, hidden]` — a single packed row — than to `[batch_size>1, seq_len, hidden]` with independent per-sample rows. So the 3D per-row branch (and its per-row-empty-mask guard) may not actually be exercised by the primary JSON-dataset data path at all.
  - It **would** be exercised by Task 6's fallback LeRobot-conversion path, *if* that path produces genuine multi-row batches — but that path won't automatically inherit the primary path's implicit guarantee that every sample has a `<state>` token, unless whoever writes that converter deliberately preserves/enforces it. Worth double-checking when Task 6 is implemented, and worth a deliberate look at Task 7 Step 6 (real training-loop wiring) to confirm which shape actually shows up at this call site before assuming the per-row branch is dead code or live code.

### Important #1: seeding, so Task 9's ablation isolates `use_m7_consolidation`

Added `--seed` (default 42) and a `_seed_everything(seed)` helper (`random.seed` + `torch.manual_seed` + `torch.cuda.manual_seed_all`), called **twice** in `main()`:

## TODO for Task 9 — the M7 consolidation term leaks gradient into the shared LoRA weights, not just adapter/memory_core

### Fix 1: documented the real CUDA-determinism limitation (investigated for real, not assumed)

The review's premise stated the VLM defaults to `attn_implementation="sdpa"`. **Correcting this for the record, based on direct inspection, not just going along with the premise:** `xr1()`'s real, active `_build_model()` (`vendor/Xiaomi-Robotics-1/xr1/mibot/models/VLA/XR1.py` line 223) explicitly passes `attn_implementation="flash_attention_2"` — confirmed by grep, not sdpa. `"sdpa"` only appears as a bare default value on an unrelated internal constructor parameter elsewhere in `qwen3vl.py` that isn't on our real construction path. This doesn't change the substance of the review's concern — flash-attention's backward pass is the same category of atomic-add-based non-determinism as sdpa's — but the fix and its documentation are about the backend actually in use, so it needed to be right.

Real investigation performed (not reasoned from memory alone), against this pod's actual torch/CUDA/flash-attn stack:
- **`torch.use_deterministic_algorithms(True)` empirically raises** on this pod for an ordinary CUDA matmul backward (`x @ w` on two 8×8 CUDA tensors, `.sum().backward()`): `RuntimeError: ... uses CuBLAS ... you must set an environment variable CUBLAS_WORKSPACE_CONFIG`. Since every `nn.Linear` backward in this ~5.4B-param model would hit the identical error, enabling this flag inside `_seed_everything` would break every real training step immediately — this is not a theoretical incompatibility, it's a reproduced one. Setting `CUBLAS_WORKSPACE_CONFIG` would need to happen as a process env var before CUDA initializes, which `_seed_everything` (called from `main()`, after argparse and well into the process) cannot reliably guarantee. **Not enabled**, for this concrete, evidenced reason.
- **Even if the cuBLAS issue were solved, it wouldn't fix the real bottleneck.** flash-attention's CUDA kernel is an external autograd Function, invisible to PyTorch's ATen dispatcher — `torch.use_deterministic_algorithms()` has no hook into it at all (confirmed by reading how the flag is implemented: it only affects PyTorch-registered ops). So the flag would add real breakage risk (the cuBLAS error above) for zero benefit against the actual dominant non-determinism source.
- **Real, useful finding worth flagging for later:** `inspect.signature()` on the installed `flash_attn==2.8.3`'s `flash_attn_func`/`flash_attn_varlen_func` shows both **do** expose a real `deterministic=False` kwarg (i.e. the underlying library supports a slower, deterministic backward mode). But grepping the installed `transformers==4.57.1`'s `transformers/integrations/flash_attention.py` for `"deterministic"` returns **zero matches** — the HF integration glue our model goes through never forwards that kwarg to flash-attn at all. Reaching true attention-backward determinism would require monkeypatching/wrapping that integration to pass `deterministic=True` through — a real, concrete, but out-of-scope architecture change for this fix cycle. Documented here as the actual path forward if full CUDA determinism is ever required (e.g. for a stricter later reproducibility bar), not attempted now.
- **Added `torch.backends.cudnn.deterministic = True` and `torch.backends.cudnn.benchmark = False`** to `_seed_everything` — low-risk (unlike `use_deterministic_algorithms`, confirmed these don't raise), and give real (if minor) benefit for the vision tower's `Qwen3VLVisionPatchEmbed`'s `nn.Conv3d` patch-embed layer, which does route through cudnn.
- Full reasoning is also inline in `_seed_everything`'s own docstring in `code/finetune_run.py`, so it's visible at the call site, not just here.

**Bottom line for Task 9:** `--seed` guarantees identical LoRA init, identical DataLoader batch order (with `--num-workers 0`), and identical `xr1.forward()`-internal Python/torch-RNG-driven choices (prefix_length, timestep sampling) between a LoRA-only and a LoRA+M7 run. Two runs with the same seed will be *close* but not necessarily bit-identical beyond the first forward pass — small numeric drift beyond step 1 should be expected and isn't itself evidence of a seeding bug (distinct from the real, larger, and expected divergence documented in the "TODO for Task 9" section above, which is caused by the M7 gradient leak, not CUDA nondeterminism).

### Real CPU-RAM peak fix in `load_xr1_with_checkpoint()` -- measured, not theoretical

**Real, concrete danger found during the smoke test above, by direct repeated polling** (not assumed): this pod's cgroup memory ceiling (`/sys/fs/cgroup/memory.max` = 167.0GB, shared with the 6 paused SIGSTOP'd M7 trimodal jobs -- ~4.5-4.6GB RSS each, kept resident even while stopped -- and the CPU-only ODI job at ~16.5GB RSS) left as little as **23MB free** (`memory.current`) during the original (pre-fix) checkpoint-loading phase of the very first robocasa smoke test, confirmed by a 3-second-interval poll loop logging `ps -o rss=` + `cat /sys/fs/cgroup/memory.current` throughout the run. `memory.events`' `oom`/`oom_kill`/`oom_group_kill` counters stayed at 0 (survived via direct reclaim), but this was a real, near-miss margin, not a comfortable one -- consistent with the pattern that killed the earlier washer-data LoRA+M7 training attempts silently (no traceback) before this pivot even started.

**Real root cause, traced by reading `load_xr1_with_checkpoint()` directly**: the original code did `state_dict = {}; for shard_path in shard_paths: state_dict.update(load_file(shard_path, device="cpu"))` -- accumulating **all 3 safetensors shards (~9.5GB combined: 4.99GB + 5.00GB + 0.12GB)** into one CPU dict simultaneously, held alongside `xr1()`'s own already-allocated bf16 random-init parameters (~10GB, unavoidably allocated at `xr1()` construction time, before any checkpoint loading starts). Real measured peak RSS during this phase: **~20.4GB**.

**`low_cpu_mem_usage=True` (HF's own `from_pretrained` kwarg) does not apply here**, confirmed by reading `XR1.py`'s `_build_model()` directly: it calls `Qwen3VLForConditionalGeneration._from_config(config, attn_implementation="flash_attention_2", dtype=torch.bfloat16)`, not `from_pretrained` -- there is no real trained checkpoint available to lazily materialize from at construction time; the checkpoint is loaded separately, afterward, by `load_xr1_with_checkpoint` itself. A full `torch.device("meta")` reconstruction of `xr1()` (the real `low_cpu_mem_usage`-equivalent mechanism -- build on meta, then `load_state_dict(..., assign=True)` to materialize real weights directly with no double allocation) was investigated and **deliberately not attempted**: it would leave several real submodules as literal unusable `meta` tensors after loading, since they are never covered by the checkpoint's own state dict -- `state_projector_choice`/`action_projector_choice`/`score_projector_choice` (used every training forward pass, not just at inference), `vlm.model.action_embed`/`score_embed`, the tied `vlm.lm_head.weight` (needs an explicit `tie_weights()` re-call), and potentially non-persistent buffers such as RoPE `inv_freq` (recomputed at construction, never checkpoint-persisted, and unlike the others has no generic `reset_parameters()` recovery path). Correctly and safely materializing every one of these would be real, individually-verified engineering beyond what could be landed and verified with confidence in the time available for this fix cycle -- flagged here as a legitimate follow-up if CPU-RAM pressure ever requires a deeper fix than what was applied.

**Fix actually applied (real, low-risk, matches the "load shard-by-shard" mechanism suggested as a real alternative)**: shards are now loaded and merged into the model **one at a time** -- `load_file(shard_path)` -> `model.load_state_dict(shard_state_dict, strict=False)` (accumulating which keys were loaded across shards, since each shard covers disjoint keys) -> `del shard_state_dict; gc.collect()` -- before the next shard is even read from disk. This bounds the state-dict-side peak to the size of the **largest single shard (~5.0GB)** rather than all 3 combined (~9.5GB). `assign=True` is deliberately NOT used here (that's only needed to avoid double-allocation against a *meta*-device model with no real storage to copy into -- `xr1()`'s own real, pre-allocated parameter storage is reused via the default copy-based `load_state_dict`, exactly as before; this fix only reduces how much of the *checkpoint's own raw bytes* are ever resident at once, not how the model's own memory is held).

**Real, measured before/after (identical smoke test methodology, same 3-second polling loop, same batch_size=4/total_steps=3 run)**:

| | Before fix | After fix |
|---|---|---|
| Process RSS peak during checkpoint load | **~20.4GB** (`rss_kb=20439648` at 17:44:18) | **~10.2GB** (`rss_kb=10209996` at 17:55:40) |
| Real reduction | -- | **~50%**, matches the "largest single shard vs all 3 combined" mechanism exactly |
| `oom_kill` counter | 0 (survived) | 0 (survived) |
| Training result | 3/3 steps, finite losses, DiT untouched verified | 3/3 steps, finite losses (`1.782514`/`2.519390`/`2.694729` -- matches the before-fix run within the small run-to-run flash-attention-backward numeric noise already documented in Task 7's CUDA-determinism notes), DiT untouched verified (identical `87388.32329446077`) |

**Honest caveat, not glossed over**: this fix demonstrably and meaningfully reduces *this process's own* contribution to CPU-RAM pressure (the piece actually under this codebase's control), but the cgroup-wide `memory.current`/`memory.max` margin still oscillated close to zero for a sustained stretch during the after-fix run too (bounded by the OTHER long-running jobs' resident footprint on this shared pod, which this fix has no influence over). `oom_kill` stayed 0 in both runs -- this pod's cgroup reliably reclaims reclaimable cache under pressure rather than killing -- but that is not a guarantee against a future large, non-reclaimable, atomic allocation. The real, load-bearing win from this fix is a genuine ~50% reduction in this one process's own peak footprint during the highest-risk phase (checkpoint load), which is the correct, real, and now-measured scope of what was asked.

## Root-cause investigation and fix -- LoRA+M7-on-realdata catastrophic collapse (atomic_seen 1.00%, composite_seen 0.00%, composite_unseen 0.75%, overall 0.6%)

**Real root cause, found and fixed: `code/robocasa_lerobot_dataset.py`'s `__getitem__` copied the raw lerobot `action` parquet column straight into the model's 12 active action-head dims with no remap -- but the raw column's own on-disk field order (per `meta/modality.json`: `base_motion[0:4]`, `control_mode[4:5]`, `end_effector_position[5:8]`, `end_effector_rotation[8:11]`, `gripper_close[11:12]`) is NOT the same order the model's action head was actually calibrated against.** The real ground truth for what the model's 12 active action-head dims mean at inference time is `robocasa.utils.env_utils.convert_action` (`/workspace/robocasa-deps/robocasa/robocasa/utils/env_utils.py` line 142 -- the function the real, working eval client, `eval_robocasa365/entry.py`, calls on every single `env.step` to turn the model's raw output into an actual robot command): `action[0:3]=end_effector_position`, `[3:6]=end_effector_rotation`, `[6:7]=gripper_close`, `[7:11]=base_motion`, `[11:12]=control_mode` -- a completely different field order. The loader's own module docstring had asserted "this dataset's raw action column IS already the real robocasa365 12-dim action-head target, no transform needed" -- this claim was **never actually checked against `convert_action`**, only against the raw modality.json field labels, and was wrong.

**This bug is NOT specific to `use_m7_consolidation` -- it affects both real-RoboCasa-data ablation legs identically.** Real evidence: aggregating `lora_only_realdata`'s partial-run result files (`eval_results/lora_only_realdata/scheduler/20260907-192751/results/*.json`, 489 real per-episode records from the run the user deliberately abandoned early) gives **7/489 = 1.4% success**, with successes concentrated entirely in `NavigateKitchen` (7/50 = 14%) and **zero** successes across all other 9 sampled tasks (`CloseBlenderLid`, `CloseFridge`, `CloseToasterOvenDoor`, `CoffeeSetupMug`, `OpenCabinet`, `OpenDrawer`, `OpenStandMixerHead`, `PickPlaceCounterToCabinet`, `PickPlaceCounterToStove`) -- the same pattern as the reported `lora_plus_m7_realdata` collapse (only `NavigateKitchen` nonzero, 8/50).
