## Task 5 — pooled hidden-state adapter: NaN-on-empty-row bug found and fixed, packing note for Task 7

- **Bug found by review, fixed before Task 7 wires this in:** `pool_state_token_hidden_states`'s 3D (batched) branch originally only validated `state_token_mask.any()` across the *whole* tensor, not per-row. An all-False mask on a single row in an otherwise-valid batch (e.g. shape `[2,3,2]`, mask `[[True,False,True],[False,False,False]]`) silently produced `[[2.,2.],[nan,nan]]` instead of raising — `.mean(dim=0)` over an empty selection is a silent NaN, not an exception. This is now fixed with a per-row check (`state_token_mask[i].any()`) that raises `ValueError(f"state_token_mask row {i} has no True positions to pool over")` identifying the offending row. Verified fixed: reproducing the exact `[2,3,2]` scenario above now raises instead of returning NaN. Added 3D test coverage (`tests/test_pooled_hidden_adapter.py`): a batched happy-path test and a per-row-empty-mask test — the 3D branch had zero test coverage before this fix (all original 3 tests only exercised the 2D single-sample path).

- **Why this matters for Task 7:** `compute_total_loss` (not yet built) has no runtime `isfinite` guard per current design. A silent NaN from this adapter would flow uncaught into the loss and permanently poison Adam's optimizer state (NaN moment estimates don't self-heal) — the kind of bug that surfaces hours into a training run with no clear proximate cause. Task 7's implementer should either keep relying on this ValueError as the guard (i.e. never suppress/catch it upstream without deliberately deciding what an empty-mask row *means* for that batch), or add an explicit `isfinite` check in `compute_total_loss` as defense in depth.

- **Real batch shape at Task 7's call site is probably NOT a genuine multi-row batch.** `vendor/Xiaomi-Robotics-1/xr1/mibot/data/collate/custom_collate.py` **packs** samples together via `torch.cat(dim=1)` (concatenating along the sequence dimension) rather than padding samples into independent rows of a batch, and it drops any sample that would overflow the packed length whole (not truncating it). This means the real `hidden_states`/`state_token_mask` tensors reaching this adapter from the primary JSON-dataset path (`xr1/mibot/data/datasets/json_dataset.py`) are likely shaped closer to `[1, total_packed_length, hidden]` — a single packed row — than to `[batch_size>1, seq_len, hidden]` with independent per-sample rows. So the 3D per-row branch (and its per-row-empty-mask guard) may not actually be exercised by the primary JSON-dataset data path at all.
  - It **would** be exercised by Task 6's fallback LeRobot-conversion path, *if* that path produces genuine multi-row batches — but that path won't automatically inherit the primary path's implicit guarantee that every sample has a `<state>` token, unless whoever writes that converter deliberately preserves/enforces it. Worth double-checking when Task 6 is implemented, and worth a deliberate look at Task 7 Step 6 (real training-loop wiring) to confirm which shape actually shows up at this call site before assuming the per-row branch is dead code or live code.

### Important #1: seeding, so Task 9's ablation isolates `use_m7_consolidation`

Added `--seed` (default 42) and a `_seed_everything(seed)` helper (`random.seed` + `torch.manual_seed` + `torch.cuda.manual_seed_all`), called **twice** in `main()`:
1. **Before model construction** — so LoRA's `kaiming_uniform_`-initialized `lora_A` starts from the same weights in both a LoRA-only and a LoRA+M7 run (both branches call `xr1()` → checkpoint load → `freeze_and_inject_lora()` identically before any mode branching, so one seed call here is sufficient for LoRA init parity).
2. **Immediately before the training loop** — because LoRA+M7 mode's `PooledHiddenAdapter`/`M7MemoryCore` construction (which only happens in that mode) draws extra RNG samples from the *global* torch RNG that LoRA-only mode never draws, which would otherwise desynchronize `xr1.forward()`'s own internal stochasticity (`prefix_length` via `random.randint`/`random.random`, the `Beta`-sampled flow-matching timestep, `torch.randn_like` noise) between the two modes from that point on — differences that would have nothing to do with `use_m7_consolidation` itself. Re-seeding right before the loop resynchronizes both runs' global RNG state entering it.

`build_dataloader()` now takes a `seed` argument and builds the shuffling `DataLoader` with its own dedicated `torch.Generator().manual_seed(seed)` (not the global RNG) — so batch order is reproducible given the same seed regardless of how much global RNG state upstream construction consumed, independent of the two re-seed calls above.

**Real confirmation this works, not just asserted:** re-ran both smoke tests with `--seed 42 --total-steps 2 --batch-size 8`. Step 1's `xiaomi` sub-loss came out **bit-identical** between modes: LoRA-only `total_loss=5.109192` (breakdown `xiaomi: 5.10919189453125`) vs LoRA+M7 `breakdown={'xiaomi': 5.10919189453125, 'consolidation': 0.3167765736579895, ...}` — same batch, same `xr1.forward()` internal randomness, same starting LoRA weights, confirmed by the identical xiaomi loss value down to the last printed digit. Step 2 diverges slightly (`xiaomi: 6.554897785186768` LoRA-only vs `6.555253028869629` LoRA+M7) — **this is real, expected signal, not a seeding failure**: `pooled_hidden` is not detached before entering `adapter`/`memory_core`, so gradients from `consolidation_loss` backpropagate through the shared VLM forward graph back into the LoRA weights themselves (not just into the adapter/memory_core parameters in isolation) — meaning LoRA+M7's LoRA weight update after step 1 legitimately differs from LoRA-only's, and that's the actual causal effect Task 9's ablation is meant to measure. Worth flagging for whoever writes Task 9's results: the M7 term isn't a pure add-on regularizer sitting outside the LoRA gradient path — it genuinely shapes the LoRA update too, via the shared hidden states.

**Caveat, not fully solved by this fix:** with `--num-workers > 0`, `JsonDataset`'s `_augment`/`_prompt` methods use stdlib `random` calls that execute inside DataLoader worker processes, whose `random`-module seeding is not covered by `_seed_everything`'s main-process seeding (PyTorch's own per-worker seeding via a passed `generator=` only covers `torch`'s RNG inside workers, not stdlib `random`). **Recommendation for Task 9: run both ablation legs with `--num-workers 0`** if bit-for-bit-reproducible image augmentation/prompt selection matters for the comparison; the smoke tests re-run above used `--num-workers 0` for exactly this reason.
